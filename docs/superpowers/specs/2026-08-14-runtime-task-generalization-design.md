# 运行时通用任务会话设计

状态：待用户书面审核

日期：2026-08-14

适用范围：`D:\python\CommandCenter\CommandCenter`

## 1. 背景

CommandCenter 已经能够通过 Skill 把 MES 查询结果写入采购业务系统，也已经验证动态 Skill Action、来源业务记录绑定和幂等创建。当前入口仍以按钮和特定演示链路为主，面对新的业务系统、不同输入结构或需要补充信息的任务时，缺少统一的运行时交互与执行协议。

本阶段建设“运行时泛化”能力：用户用自然语言或业务按钮发起任务，智能体根据已发布 Skill 和可用 Tool 理解意图、读取上下文、补齐输入、生成执行计划并执行。录制、学习和 Skill 生成能力暂不修改；本阶段消费已有 Skill，不重新设计 Skill 录制。

## 2. 目标

1. 用统一的有状态任务会话承载自然语言入口和按钮入口；
2. 根据业务语义选择已有 Skill 和 Tool，不依赖采购关键词、固定字段或专用路由；
3. 自动读取允许的业务上下文，并在信息不足时与用户继续交互；
4. 简单缺失字段通过对话询问，复杂对象、数组和日期通过临时动态表单收集；
5. 只读任务可以直接执行，所有写任务必须先展示完整计划并取得确认；
6. 将智能体判断与确定性安全边界分离；
7. 对幂等、重试、部分失败、恢复和审计提供稳定协议；
8. 保持现有按钮、Skill Action 和业务专用兼容接口可用。

## 3. 非目标

- 不修改浏览器扩展录制协议；
- 不重新录制或自动生成 Skill；
- 不在本阶段实现任意网页点击回放或桌面 RPA；
- 不让模型绕过已发布 Skill、Tool 白名单、权限或 Schema；
- 不把采购业务字段固化为通用任务模型；
- 不为每一种交互建立独立业务页面；
- 不实现无明确补偿定义的自动回滚；
- 不移除现有采购查询、详情、进度追踪或创建跟进任务接口。

## 4. 方案选择

采用“持久化有状态任务协议”。每个用户目标创建一个 `TaskSession`，服务器保存状态、消息、解析上下文、输入、计划、确认和步骤结果。前端只渲染服务器返回的下一种交互，不在页面内编排业务流程。

未采用的方案：

- 一次性自然语言执行：实现简单，但无法可靠补充输入、确认写操作、从中断处恢复或展示可审计过程；
- 前端工作流编排：交互直观，但会把 Skill 语义和业务字段重新硬编码到界面，不能泛化；
- 完全自由的聊天代理：灵活但安全边界、幂等和执行状态难以验证，不适合企业写操作。

## 5. 总体架构

### 5.1 TaskSession 状态机

任务状态按以下顺序推进：

```text
understanding
→ resolving_context
→ collecting_input
→ awaiting_confirmation
→ executing
→ verifying
→ succeeded | failed
```

只读任务在计划通过验证后可从 `collecting_input` 直接进入 `executing`。如果当前信息已经完整，前面的状态可以在一次服务调用内连续推进，但每次持久化后的状态必须符合允许的状态转换。

`failed` 是本次执行的终态，不代表任务不可重新发起。用户修正目标或输入时创建新的计划修订；已经发生的外部副作用仍保留证据，不能通过改写历史状态假装未发生。

### 5.2 组件职责

#### TaskSessionService

负责创建和持久化任务会话、验证状态转换、并发版本、计划修订及下一交互。它不判断业务语义。

#### IntentAndSkillAgent

根据用户目标、当前页面上下文、已发布 Skill 目录和 Tool 描述，提出目标业务对象、Skill、操作意图及所需输入。无法唯一确定时返回候选项，不猜测。

#### ContextResolverAgent

仅使用允许的只读 Tool 获取候选业务对象和补充上下文。其证据写入会话，并标注来源 Tool、查询参数、对象标识和采集时间。

#### InputCollector

比较 Skill 输入 Schema、可信上下文和用户已提供内容，决定下一次交互：

- 单个或少量标量字段使用对话问题；
- 枚举或多个候选对象使用选择；
- 对象、数组、日期组合或多字段约束使用基于 JSON Schema 的临时表单。

InputCollector 只决定交互形式和收集值，不自行放宽 Skill Schema。

#### ExecutionPlanAgent

生成可审计的执行计划，包括固定 Skill 版本、步骤顺序、Tool、读写性质、目标对象、参数来源、验证方式、幂等和可选补偿定义。

#### PlanValidator

使用确定性代码验证 Skill 版本、Tool 白名单、权限、Schema、参数来源、目标对象、写步骤幂等条件、资源限制和确认要求。验证失败返回明确错误，不静默修改计划来替代智能体判断。

#### ConfirmationGate

所有写计划在执行前进入确认状态。确认只覆盖页面完整展示的当前计划；只读计划不要求确认。

#### GenericSkillExecutor

按已验证计划调用通用 Skill/Tool 执行接口，记录每一步请求摘要、响应摘要、幂等键、状态和证据。它不包含采购专用字段映射或路由分支。

#### ResultVerifier

根据计划中声明的验证步骤回读或检查结果，区分“调用已成功”和“业务结果已验证”。无法验证时报告验证不完整，不把它标记为完整成功。

## 6. 会话与交互协议

### 6.1 TaskSession 核心数据

任务会话至少保存：

- `session_id`、用户/租户/权限上下文；
- 当前 `state` 和用于乐观并发控制的 `version`；
- 原始目标及后续消息；
- 候选和已选业务对象、Skill 与版本；
- 只读上下文证据；
- Skill 输入 Schema、已收集输入及每个值的来源；
- 当前 `plan_revision`、规范化执行计划及 `plan_hash`；
- 确认记录和确认令牌消费状态；
- 每个执行步骤的状态、幂等键、结果及验证证据；
- 最终结果或结构化失败信息。

会话不保存明文凭证、浏览器 Cookie、访问令牌或 API 密钥。Tool 在执行时从受控凭证存储中解析授权。

### 6.2 统一下一交互

服务端返回一个 `next_interaction`，类型限定为：

- `message`：解释状态、限制或非阻塞信息；
- `question`：收集简单字段；
- `selection`：要求用户选择 Skill、业务对象或枚举值；
- `form`：返回 JSON Schema 和当前值，渲染临时动态表单；
- `confirmation`：展示完整写计划、影响对象和风险，等待确认；
- `result`：展示成功结果、失败步骤、验证状态和后续建议。

每个需要提交的交互携带当前会话 `version`。过期版本的提交返回冲突和最新交互，避免两个页面或重复点击覆盖彼此。

### 6.3 建议 API

```text
POST /task-sessions
POST /task-sessions/{session_id}/messages
POST /task-sessions/{session_id}/inputs
POST /task-sessions/{session_id}/confirmations
GET  /task-sessions/{session_id}
```

`POST /task-sessions` 同时支持自然语言目标和按钮携带的结构化提示。按钮只是创建会话的快捷入口，可以预填 action、Skill 或可信业务对象，但不能绕过解析、计划验证和写确认。

## 7. 端到端数据流

1. 用户通过自然语言或按钮创建任务会话；
2. IntentAndSkillAgent 根据已发布目录提出 Skill、目标对象和输入需求；
3. 若 Skill 或业务对象不唯一，服务器返回 `selection`；
4. ContextResolverAgent 使用只读 Tool 获取可信上下文；
5. InputCollector 将上下文映射到 Skill 输入，并通过问题或临时表单补齐缺失值；
6. ExecutionPlanAgent 生成固定 Skill 版本的规范化计划；
7. PlanValidator 验证权限、Schema、对象、Tool、资源边界和副作用；
8. 只读计划直接执行；写计划生成 `plan_hash` 并返回 `confirmation`；
9. 用户确认后，ConfirmationGate 验证确认绑定和单次消费状态；
10. GenericSkillExecutor 顺序执行步骤并持久化每一步结果；
11. ResultVerifier 按计划验证业务结果；
12. 服务返回结构化 `result`。

## 8. 写操作确认

所有具有外部副作用的步骤均视为写操作，包括创建、更新、删除、发送、提交和触发远程流程。

确认页面必须完整展示：

- 将执行的 Skill 及版本；
- 将读取和写入的系统；
- 目标业务对象；
- 每个写步骤的关键参数或可理解摘要；
- 预期副作用、验证方式和已声明补偿；
- 计划修订号。

确认令牌绑定 `session_id + plan_revision + plan_hash`，只能消费一次。业务对象、Skill 版本、写入系统、参数、步骤或副作用发生任何变化，都必须生成新修订并重新确认。纯展示文案变化且规范化计划未变，不需要重新确认。

## 9. 安全边界

智能体负责语义理解、Skill 选择、参数映射、冲突解释和计划建议。确定性代码只执行稳定边界：

- 身份、租户、权限和 Tool 白名单；
- 已发布 Skill 版本约束；
- 请求/响应和 Skill 输入输出 Schema；
- 参数来源必须能追溯到用户输入、可信上下文或已验证步骤输出；
- 写操作确认和确认令牌绑定；
- 幂等、超时、重试、并发和调用次数限制；
- 凭证隔离、日志脱敏和审计证据；
- 明确声明并验证过的补偿范围。

不使用关键词匹配、任意阈值或采购样例分支替代智能体的业务判断。若未来把某项判断下沉为代码规则，必须说明它保护的稳定不变量、对未知场景泛化的影响以及如何配置或移除。

## 10. 幂等、重试与恢复

### 10.1 幂等写

平台为每个写步骤生成与业务操作稳定绑定的幂等标识。该标识不能只使用会话中的瞬时请求编号；它应至少区分租户、Skill、计划修订、步骤和目标业务对象。

只有目标 Tool 接受该幂等键，或能明确证明自身具有等价幂等语义时，才视为具备端到端幂等保障。具备保障的同一已确认业务写入在网络重试后必须命中原结果。目标 Tool 不支持幂等时，仍可在用户确认后单次调用，但遇到响应不确定时不得自动重试；系统报告结果未知并要求人工核对。

### 10.2 重试分类

允许有界自动重试：

- 只读调用的临时网络或服务故障；
- 已具备幂等保障的写调用发生超时、连接中断、响应丢失或 HTTP 502/503/504；
- 重试次数、总时长和退避由确定性策略限制。

禁止自动重试：

- Schema 或参数验证错误；
- 认证、权限或租户错误；
- 明确的业务拒绝、库存/状态冲突等业务错误；
- 未提供幂等保障的写调用；
- 已经确认目标计划发生变化的调用。

“幂等写失败”不是指重复创建，而是指写请求可能已经到达目标系统，但调用方因超时或连接中断没有收到确定响应。此时以同一幂等键重试，应返回首次写入结果而不是产生第二条记录。

### 10.3 服务恢复

每一步执行前后均持久化状态。服务重启后从最近的可靠检查点恢复：

- 已有成功证据的步骤不重复执行；
- 状态不确定且具备幂等保障的写步骤使用原幂等键查询或重试；
- 状态不确定且无幂等保障的写步骤停止并报告人工核对；
- 已消费的确认令牌不能再次授权另一份计划。

## 11. 失败与部分成功

- 缺少输入：返回 `question` 或 `form`，不生成猜测值；
- Skill 或业务对象有歧义：返回 `selection`；
- 计划验证失败：保持不执行并解释具体边界；
- 明确业务错误：不重试，停止后续写步骤；
- 某一步写入成功、后续步骤失败：停止未来写步骤，保留成功步骤证据，结果标记为部分失败；
- 调用成功但回读验证失败：标记验证不完整，不伪装为完整成功；
- 并发版本冲突：拒绝过期提交并返回最新状态；
- 确认令牌过期、已消费或计划哈希不匹配：拒绝执行并要求重新确认。

系统不执行隐式回滚。只有 Skill 明确声明补偿 Tool、适用条件、参数来源和权限，且 PlanValidator 验证通过时，执行器才可以自动补偿。补偿本身是新的写步骤，必须具有审计、幂等和结果验证；补偿失败与原始失败分别报告。

## 12. 前端交互

现有自然语言面板演进为通用任务会话渲染器，按 `next_interaction` 显示消息、问题、选择、动态表单、确认或结果。前端不根据 Skill 名称或业务字段决定下一步。

现有按钮保留，但逐步改为创建带结构化提示的 TaskSession：

- “查看详情”和“追踪采购进度”可继续走兼容接口，直到对应只读 Skill 接入统一协议；
- 动态 Skill Action 和“创建采购跟进任务”按钮最终走同一 TaskSession 流程；
- 迁移期间旧接口行为和现有演示验证方法保持可用。

## 13. 测试策略

### 13.1 状态机单元测试

覆盖全部允许和禁止的状态转换、连续自动推进、乐观并发、计划修订、终态以及服务恢复。

### 13.2 安全协议测试

验证 Tool 白名单、权限、Schema、可信参数来源、写确认、`plan_hash` 绑定、单次确认、版本冲突、凭证隔离和日志脱敏。

### 13.3 通用契约测试

使用至少两个与采购无关的假系统和 Skill，覆盖不同 Schema、只读/写组合、对象选择和数组输入。测试不得依赖采购关键词、固定字段、样例 ID 或专用 API，以证明泛化来自协议而非样例分支。

### 13.4 前端交互测试

验证六种 `next_interaction` 渲染、动态表单提交、确认计划展示、过期版本恢复、部分失败和验证不完整提示。

### 13.5 端到端验收场景

1. 只读任务无需确认即可完成；
2. 缺少简单字段时通过对话补齐；
3. 复杂数组输入使用临时动态表单；
4. 写任务必须展示完整计划并确认；
5. 计划或目标对象改变后旧确认立即失效；
6. 重复提交同一已确认请求不会产生重复写入；
7. 幂等写在超时后以同一键重试并返回首次结果；
8. 明确业务失败不自动重试；
9. 多步骤部分失败时停止后续写入并分别展示步骤状态；
10. 服务重启后继续任务，不重复已有成功证据的步骤；
11. 现有采购创建跟进任务可以通过统一会话完成；
12. 现有旧接口和演示页面保持回归通过。

## 14. 第一阶段交付范围

第一阶段形成可纵向运行的最小通用协议：

1. 持久化 TaskSession 和状态转换；
2. 六种统一 `next_interaction`；
3. 已发布 Skill 的选择、输入补齐和计划生成；
4. 确定性 PlanValidator；
5. 只读直执行与写计划确认；
6. 通用 Skill 执行、步骤证据和结果验证；
7. 幂等重试、部分失败和重启恢复的最小闭环；
8. 通用前端交互渲染器；
9. 非采购通用契约测试及现有采购链路回归。

录制能力、三个以上系统的录制交互、任意网页回放和复杂审批流留待后续独立设计。

## 15. 验收标准

1. 自然语言和按钮能创建相同协议的任务会话；
2. 新 Skill 可以仅通过发布配置接入，不新增前端业务页面或后端业务专用路由；
3. 简单输入以对话收集，复杂输入以 Schema 表单收集；
4. 只读任务不要求确认，所有写任务都绑定完整计划确认；
5. 计划改变后不能使用旧确认执行；
6. 同一幂等业务写入在重复提交或暂时故障重试后只产生一个结果；
7. 部分失败、验证不完整和结果未知能被准确区分并审计；
8. 服务重启不会重复执行已有成功证据的步骤；
9. 至少两个非采购假 Skill 通过同一协议完成契约测试；
10. 采购跟进任务作为验收样例通过统一会话完成，且代码中没有为其新增关键词、固定字段或专用分支；
11. 现有兼容接口与演示验证流程不受破坏；
12. 本阶段没有修改 Skill 录制能力。
