# 演示失败阶段与原因反馈设计

状态：已实施

日期：2026-07-30

适用范围：CommandCenter V1 演示工作台

## 1. 问题

当前后端把所有未发布的学习结果统一转换为 `needs_reteach`，前端又把
`needs_reteach` 固定解释为“自动测试没有通过”，并将进度定位在测试阶段。

因此，当智能体在演示分析阶段判定 `compilable=false` 时，页面错误地显示为测试
失败。实际上此时没有生成候选 Skill，也没有执行自动测试。

## 2. 目标

页面必须准确区分以下失败位置：

1. 演示分析或 Skill 编译失败；
2. 无害测试失败；
3. 系统调用异常。

状态分类由代码根据 LangGraph 已执行到的确定性节点生成；具体业务原因继续来自
智能体分析、测试结果或异常信息，不在前端硬编码业务判断。

## 3. 方案

保留现有终态 `needs_reteach`，在录制结果中增加：

- `failure_stage`：`analysis`、`testing` 或 `system`；
- `failure_reasons`：面向用户的原因列表。

这样既不改变“失败后允许重新演示”的现有交互，也不要求前端解析
`learning_result` 的内部结构。

不采用以下方案：

- 为每个失败位置增加独立录制状态：表达清晰，但会扩大现有 API 和页面状态机；
- 由前端检查 `candidate_skill`、`test_results` 等字段推断：改动少，但前端会依赖
  LangGraph 内部数据结构，容易再次误判。

## 4. 后端行为

学习图返回被拒绝时：

- 如果分析结果为 `compilable=false`，返回 `failure_stage=analysis`；
- 原因优先使用智能体的 `uncertainties[].description`，没有时使用分析摘要；
- 如果执行过无害测试但未满足发布条件，返回 `failure_stage=testing`；
- 原因来自失败测试结果；
- 未捕获异常由服务层标记为 `failure_stage=system`，并提供不泄露密钥等敏感信息的
  用户提示。

录制的顶层状态仍为 `needs_reteach`，详细学习记录仍保存在 `learning_result`。

## 5. 前端行为

演示工作台根据 `failure_stage`：

- `analysis`：高亮“学习”，显示“演示内容无法生成 Skill”；
- `testing`：高亮“测试”，显示“自动测试没有通过”；
- `system`：不伪装成业务测试失败，显示“系统处理失败”；
- 逐条展示 `failure_reasons`。

若旧记录没有新增字段，使用中性的兼容提示“本次演示未能发布 Skill，请查看原因后
重新演示”，不再默认声称自动测试失败。

## 6. 测试

后端回归测试覆盖：

1. `compilable=false` 时返回分析阶段及智能体原因；
2. 无害测试拒绝发布时返回测试阶段及测试失败原因；
3. 发布成功时不返回失败字段。

前端回归测试覆盖：

1. 分析拒绝高亮学习阶段并显示分析原因；
2. 测试拒绝高亮测试阶段并显示测试原因；
3. 缺少失败详情的旧记录显示中性提示。

## 7. 完成标准

使用“任务派发”错误演示时，页面明确说明演示调用的接口无法生成采购 Skill，并
停留在学习阶段；只有真实执行过无害测试且失败时，页面才显示“自动测试没有通过”。
