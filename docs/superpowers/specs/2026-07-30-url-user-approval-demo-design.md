# URL 用户与采购审批演示设计

状态：已实施

## 1. 目标

在不建设登录页面、密码、令牌和正式权限系统的前提下，演示两个用户之间的采购任务流转：

```text
u001 普通员工在中控发起采购请求
→ 中控调用已发布 Skill
→ 采购业务系统创建采购申请
→ 采购业务系统同时生成一条审批待办并分配给 u002
→ u002 打开自己的中控后看到该待办
→ u002 可以用现有任务表单完成处理
```

该功能只服务于本地测试与演示，不声称具备真实身份认证或访问控制能力。

## 2. 测试用户

- `u001`：普通员工、采购申请人；
- `u002`：采购审批人。

用户身份由中控网址的 `user` 查询参数提供：

- `http://127.0.0.1:5173/?user=u001`
- `http://127.0.0.1:5173/?user=u002`

参数缺失或不是已知测试用户时，回退为 `u001`。

## 3. 身份与业务边界

中控负责保存当前页面的测试用户上下文，并把用户编号用于：

- 页面右上角的当前用户显示；
- 查询该用户的待办和已完成任务；
- 提交该用户处理的任务结果。

采购业务系统仍是采购申请和审批任务的事实来源。它负责：

- 保存采购申请；
- 创建审批任务；
- 保存 `assignee_id=u002`；
- 按 `operator_id` 返回各用户的任务；
- 校验任务只能由对应处理人完成。

V1 不建立独立用户数据库。代码中的两个测试用户属于确定性的演示环境配置，不参与智能体的语义判断。

## 4. 采购申请后的待办生成

`POST /api/purchase-requests` 成功创建采购申请后，在同一数据库事务中创建一条审批任务：

- `task_type`：`purchase_review`；
- `form_code`：`purchase_task_result`；
- `assignee_id`：`u002`；
- 内容：采购单号、物品、数量、原因和申请人；
- 状态：`pending`。

接口响应增加审批任务编号。已有幂等键命中时直接返回原响应，不重复创建采购申请或审批任务。

## 5. 前端行为

任务中心从 URL 读取当前用户，不增加登录页。

打开 `?user=u001`：

- 显示普通员工身份；
- 可用自然语言发起采购请求；
- 只看到分配给 `u001` 的任务。

打开 `?user=u002`：

- 显示采购审批人身份；
- “待办任务”中出现新生成的采购审批；
- 可以继续使用已有动态表单完成任务。

V1 不自动实时推送。新任务创建后，`u002` 页面通过点击“刷新待办”或重新打开页面读取最新任务。

## 6. 明确不做

- 登录、退出和密码；
- JWT、Cookie 会话和真实鉴权；
- 用户注册、编辑和组织架构；
- 动态审批规则；
- 消息推送和通知中心；
- 多级审批、转交、加签和抄送。

## 7. 测试

后端测试覆盖：

1. 创建采购申请时同时创建一条分配给 `u002` 的审批任务；
2. 幂等重试不重复创建审批任务；
3. `u001` 查询不到 `u002` 的待办；
4. `u002` 能查询并完成自己的待办。

前端测试覆盖：

1. 无 URL 参数时使用 `u001`；
2. `?user=u002` 时以 `u002` 查询任务；
3. 未知用户参数回退为 `u001`；
4. 页面显示当前测试用户及角色。

## 8. 完成标准

用两个浏览器标签页分别打开 `u001` 和 `u002`：

1. `u001` 发起“采购签字笔”；
2. 采购业务系统产生一条采购申请；
3. `u002` 刷新待办后看到对应采购审批；
4. `u001` 看不到这条分配给 `u002` 的待办；
5. `u002` 可以提交处理结论；
6. 后端测试、前端测试和前端构建通过。
