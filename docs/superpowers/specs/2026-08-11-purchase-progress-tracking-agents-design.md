# 采购进度追踪智能体设计

状态：待用户书面审核

日期：2026-08-11

适用范围：`D:\python\CommandCenter`

## 1. 背景

现有版本已经完成采购申请列表、请购人筛选、分页和详情查询的只读 Tool 闭环。用户可以用自然语言查询采购申请，但还需要自己理解某条申请与采购订单、收货及入库记录之间的关系。

下一步增加一条最小跨对象业务链路：用户只提供请购人、日期、物料等已知业务信息，中控查询候选采购申请；用户选中一条后，中控自动追踪该申请对应的采购订单和收货/入库情况。

用户不需要知道或输入 `CGSQ26042201` 之类的内部申请单号。内部编号只作为系统连接业务对象的证据。

## 2. 目标与非目标

### 2.1 目标

1. 支持从自然语言业务条件查找采购申请候选记录；
2. 支持用户从候选记录选择一条并发起“追踪采购进度”；
3. 自动追踪“采购申请 → 采购订单 → 收货/入库”只读链路；
4. 使用 LangChain Agent 完成动态 Tool 选择和逐步观察；
5. 使用 LangGraph 编排多个智能体角色、共享状态和失败路径；
6. 展示可读进度摘要及每一阶段的原始业务证据；
7. 对 Tool 选择、参数、返回和关联判断保留脱敏审计记录；
8. 保持现有采购查询、详情和 Skill 录制闭环可用。

### 2.2 非目标

- 不执行新增、修改、提交、审核、生成、删除等 MES 写操作；
- 不追踪发票、付款或财务结算；
- 不要求用户理解或输入 MES 内部 ID、申请单号或订单号；
- 不一次性开放整个 MES 的全部 API；
- 不自动把采购追踪链路保存为 Skill；
- 不重写现有 Skill 录制、分析和验证流程；
- 不在本轮迁移全部旧智能体到新 Runtime；
- 不把三个智能体部署为三个独立服务。

## 3. 技术方案选择

本轮采用 **LangChain Agent + LangGraph**：

- LangChain `create_agent` 提供模型、Tool、Tool 结果回填、连续调用、停止条件和 Middleware 等通用 Agent Loop；
- LangGraph 继续作为业务编排层，管理角色切换、共享状态、确定性检查点、失败分支和最终输出；
- Pydantic 继续定义 Tool 参数、智能体交接和最终结果协议；
- 现有 `AgentRuntime` 抽象保留，Microsoft Agent Framework Adapter 继续作为可替换试验实现，但不作为本轮主路径。

选择该方案的原因是项目已经以 LangGraph/LangChain 为主栈，可以直接复用当前模型配置、状态和 Tool 基础设施，避免同时维护两套业务编排机制。

## 4. 用户流程

1. 用户输入自然语言，例如“查询孟明佳最近的采购进度”。
2. 任务理解智能体提取请购人、日期、物料等业务条件并调用采购申请列表 Tool。
3. 若没有结果，中控提示用户调整查询条件。
4. 若只有一条结果，中控仍展示该记录并允许用户确认追踪。
5. 若有多条结果，中控展示候选列表，不由智能体猜测用户所指记录。
6. 用户点击某条记录的“追踪采购进度”。
7. 系统从已保存且可信的查询结果取得申请单号等关联字段，不接受前端任意注入内部编号。
8. 追踪执行智能体逐步查询对应采购订单、订单明细和收货/入库记录。
9. 验证总结智能体检查关联证据并输出可读进度链。
10. 用户可以展开采购申请、采购订单和收货/入库阶段，查看原始返回证据。

第一版不在多个候选结果中自动选择“最近一条”。未来若用户明确表达“最近一笔”，可以在另一个设计切片中增加自动选择能力。

## 5. 智能体协作

### 5.1 任务理解智能体

职责：

- 理解用户查询意图和业务条件；
- 从允许的采购 Tool 中选择采购申请列表查询；
- 提取可验证的筛选及分页参数；
- 返回候选采购申请，不推测内部编号。

该角色复用现有采购申请 Tool 优先查询能力。本轮只调整其与后续追踪的交接协议，不为每种筛选条件创建 Skill。

### 5.2 追踪执行智能体

职责：

- 接收用户选中的可信采购申请记录；
- 根据当前证据选择下一项只读 Tool；
- 执行一个 Tool 后观察结果，再决定是否及如何继续；
- 支持一条申请对应零个、一个或多个采购订单；
- 支持一个订单对应零条、一条或多条收货/入库记录；
- 在证据不足、关联冲突或达到执行上限时停止。

该角色采用 LangChain Agent 的 Tool Loop，不预先写死固定的三步 API 调用。Tool 描述提供业务字段语义，智能体根据返回数据选择下一步；确定性代码只校验调用是否处于只读白名单和资源限制内。

### 5.3 验证总结智能体

职责：

- 核对各阶段对象是否通过明确业务字段关联；
- 区分“业务尚未到达下一阶段”和“技术调用失败”；
- 汇总多个订单、多次收货或多条入库记录；
- 生成用户可理解的状态、摘要和缺失信息说明；
- 不在缺少证据时补造订单、状态或关联关系。

三个角色是同一后端进程中的独立职责，由 LangGraph 编排，不增加三个独立部署单元。

## 6. LangGraph 数据流

```text
自然语言任务
    |
    v
任务理解 Agent
    |
    v
采购申请候选列表
    |
    v
用户选择可信记录
    |
    v
追踪执行 Agent <----+
    |                |
    v                |
执行一个只读 Tool    |
    |                |
    v                |
观察返回并更新证据 --+
    |
    v
验证总结 Agent
    |
    v
进度链 + 分阶段证据
```

追踪执行循环必须有最大模型调用次数、最大 Tool 次数、总超时和最大响应体限制。达到任一限制后返回受控的“不完整追踪”，不能无限继续。

## 7. 首批 Tool 范围

在现有采购申请只读 Tool 基础上，增加经过验证的采购订单及收货/入库只读 Tool：

1. 采购申请分页查询；
2. 采购申请主记录详情；
3. 采购申请明细；
4. 采购订单分页查询，可按采购申请来源单号关联；
5. 采购订单明细，可按订单主记录标识关联；
6. 采购订单收货记录，可按订单号关联；
7. 采购入库通知分页查询，可按采购订单或来源单号关联；
8. 采购入库通知明细，可按入库通知主记录标识关联。

实施前需通过现有 OpenAPI 文档和一条真实只读数据链再次核实实际请求路径、参数含义及响应结构。只有验证为读取语义的操作才能进入 allowlist。

不能只根据 HTTP `GET` 判断无副作用。MES 中具有审核、完成、生成或更新语义的 `GET` 接口仍视为写操作，本轮禁止注册为 Tool。

## 8. Tool 与安全边界

智能体负责：

- 语义理解；
- Tool 选择；
- 参数提取；
- 根据前一步结果决定下一步；
- 业务关联判断；
- 缺失和冲突解释。

确定性代码负责：

- 系统、Tool 和操作级只读白名单；
- 凭证、权限和租户边界；
- Pydantic 参数与返回协议校验；
- 可信记录选择及防止前端注入内部 ID；
- 超时、重试、模型次数、Tool 次数和响应大小限制；
- 敏感字段脱敏；
- 调用证据、关联证据和错误审计；
- 禁止任何未授权副作用。

业务字段的关联关系不能仅靠样例值硬编码。Tool 元数据和智能体上下文应说明 `sourceCode`、`orderNumber`、`mainCode` 等字段的业务含义；智能体提出关联，代码验证字段存在、来源可信且调用参数符合 Schema。

## 9. 结果展示

中控展示一条阶段化进度链：

```text
采购申请：已审核
采购订单：已生成 1 张
收货状态：已收货 2 次
入库状态：部分入库
```

每一阶段包括：

- 业务状态；
- 相关记录数量；
- 对用户有意义的核心字段；
- 未完成或缺失原因；
- 可展开的原始返回内容。

结果展示必须支持多个订单和多次收货，不能默认只显示第一条。原始 JSON 只放在折叠证据区，不作为主结果。

## 10. 异常处理

- 未找到采购申请：提示调整请购人、日期或物料条件；
- 找到多条采购申请：展示候选列表并等待用户选择；
- 尚未生成采购订单：显示“采购申请已存在，暂未生成采购订单”，属于有效业务结果；
- 已生成订单但没有收货记录：显示“采购订单已生成，尚未收货”；
- 存在多个订单或多次收货：完整汇总并允许展开；
- 不同阶段无法可靠关联：停止该分支并说明缺少的证据；
- 凭证失效：提示重新连接，不降级为浏览器写操作；
- API 超时、响应异常或 Tool 协议错误：标记为技术失败，不能解释为业务未发生；
- 模型或 Tool 达到执行上限：返回已完成阶段和“不完整追踪”原因；
- 总结智能体输出不符合 Schema：整次追踪不标记为完整成功。

## 11. 可观测性

每次追踪至少记录：

- 任务、用户选择的可信记录引用和业务系统；
- LangGraph run ID 和各智能体角色；
- 模型调用次数、耗时和结果状态；
- Tool 名称、顺序、脱敏参数、状态、耗时及响应摘要；
- 每个阶段采用的关联字段及证据来源；
- 最终追踪状态：完整、业务未推进、不完整或技术失败；
- 不保存模型隐式思维链，不记录凭证和完整敏感载荷。

这些记录继续作为 Tool 使用样例和系统学习证据，但不会自动生成 Skill。

## 12. 测试策略

### 12.1 Agent 与 Tool 单元测试

- 任务理解 Agent 能从自然语言生成正确的候选查询；
- 追踪执行 Agent 能根据前一步 Tool 返回动态选择后续 Tool；
- 不存在订单时正常停止，而不是报技术错误；
- 多订单和多收货记录不会被截断为第一条；
- 非 allowlist Tool、非法参数和副作用 Tool 被确定性边界拒绝；
- 模型次数、Tool 次数、超时和响应限制生效；
- 验证总结输出通过 Pydantic Schema。

所有自动测试默认使用 fake model 和仿真 MES 响应，不修改真实业务数据。

### 12.2 LangGraph 集成测试

- 候选查询、用户选择、追踪循环和总结节点能完整交接状态；
- 业务未推进、关联缺失、凭证失效和 API 故障进入不同分支；
- 追踪失败不影响现有查询和 Skill 录制路径；
- 每次 Tool 调用生成脱敏证据；
- LangChain Agent 的中间 Tool 结果不会跨独立任务串用。

### 12.3 真实 MES 只读验收

1. 用请购人等用户已知条件查询采购申请候选；
2. 从中控选择一条真实记录；
3. 自动追踪到对应采购订单；
4. 自动查询收货和入库情况；
5. 对照 MES 页面核验业务对象和状态；
6. 确认全过程没有新增、修改、审批、生成或删除数据；
7. 确认进度摘要与原始证据一致。

## 13. 验收标准

以下条件全部满足才算本轮闭环完成：

1. 用户无需输入内部申请单号或 MES ID；
2. 多候选场景由用户选择，系统不猜测；
3. LangChain Agent 至少完成一次基于前一步结果的动态 Tool 选择；
4. LangGraph 能编排三个智能体职责及受控失败路径；
5. 能追踪采购申请、采购订单和收货/入库三个阶段；
6. 正确表达未生成订单、未收货、部分收货和完成收货等状态；
7. 多订单、多收货记录能够完整汇总；
8. 主要结果可读，原始证据可展开核查；
9. 全部 Tool 均经过只读 allowlist 和 Schema 校验；
10. 自动测试、后端回归测试和真实 MES 只读验收通过；
11. 现有采购查询、详情和 Skill 录制闭环继续可用。

## 14. 演进方向

该闭环稳定后，可以按相同模式扩展：

1. 采购订单交付与质量状态；
2. 销售订单到生产任务；
3. 生产任务到仓储出入库；
4. 跨系统业务链路；
5. 当通用 Tool 无法表达特定工作方法时，由用户录制自定义 Skill；
6. 使用同一组测试对比 LangChain Agent 与 Microsoft Agent Framework Adapter，再决定是否迁移其他智能体角色。
