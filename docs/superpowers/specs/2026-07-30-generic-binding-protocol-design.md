# 通用绑定表达式协议设计

状态：待实施

日期：2026-07-30

适用范围：CommandCenter 多智能体之间的 Tool 参数绑定协议

## 1. 问题

演示理解智能体正确识别了采购 API，但把绑定表达式输出为
`literal('笔记本')`、`literal(1)` 等函数形式。当前执行协议只接受
`task.*`、`steps.*`、`literal.*` 路径形式，因此 Pydantic 校验失败。

现有前缀限制只写在 Pydantic 自定义校验器中，没有进入发给模型的 JSON Schema；
演示理解智能体的提示词也没有解释绑定语法。模型无法从上下文中稳定得知合法协议。

## 2. 泛化目标

修复必须适用于任意业务系统、Tool、字段和值，而不是针对采购申请增加特例。

稳定协议只有三种数据来源：

- `task.<路径>`：业务对象或上下文数据；
- `steps.<步骤标识>.output.<路径>`：前序步骤输出；
- `literal.<输入名>`：运行时自然语言或表单输入。

代码只校验协议语法，不推断业务含义，不把演示值自动替换成参数名。字段含义、参数
抽象和来源选择仍由智能体判断。

## 3. 方案

### 3.1 可见的 Schema 约束

定义一个可复用的 `BindingExpression` 类型，其 JSON Schema 包含路径前缀正则：

```text
^(task|steps|literal)\..+$
```

`BusinessAction.input_bindings[].expression` 和
`SkillStep.input_bindings` 的值都使用该类型。这样所有调用这些 Schema 的模型都能
直接看到相同约束，运行时也继续拒绝未知表达式。

正则只约束稳定的命名空间和非空路径，不限制具体系统、字段名称、步骤数量或业务
语言。

### 3.2 共享协议提示

演示理解智能体和 Skill 编译智能体共享一段简短协议说明，包含通用示例：

- `task.content.quantity`
- `steps.create.output.data.id`
- `literal.item_name`

提示明确禁止函数调用、代码表达式和直接把演示值写进绑定表达式。示例只描述协议，
不包含特定采购值或某个客户系统字段。

### 3.3 不做自动纠错

不将 `literal(value)`、模板表达式或任意代码自动转换为合法路径。自动转换需要猜测
业务参数名，可能把一次演示值错误固化进 Skill，也会扩大表达式解析和注入风险。

模型第一次输出不合法时，现有结构化重试机制会把 Schema 校验错误反馈给模型；第二次
仍不合法则安全失败。

## 4. 数据流

```text
Pydantic Schema 生成带 pattern 的 JSON Schema
→ StructuredModel 将 Schema 放入系统消息
→ 智能体按共享协议输出路径表达式
→ Pydantic 执行相同规则的运行时校验
→ LangGraph 继续分析或编译 Skill
```

Schema 是协议的机器可读来源，提示词负责解释语义；二者必须保持一致。

## 5. 错误处理

- 合法路径：进入后续智能体或 Tool 执行阶段；
- 非法路径：结构化模型携带校验错误重试一次；
- 连续失败：记录为智能体输出协议错误，不自动猜测或执行；
- API Key、网络或供应商错误继续按系统错误处理。

后续可以把“智能体输出协议错误”细分成独立可观测类型，但不属于本次最小修复。

## 6. 测试

回归测试必须覆盖：

1. `DemonstrationAnalysis` JSON Schema 对绑定表达式公开正则约束；
2. `SkillDefinition` JSON Schema 使用同一约束；
3. 合法的 `task.*`、`steps.*`、`literal.*` 表达式通过；
4. `literal(value)`、裸值和代码表达式被拒绝；
5. 演示理解和 Skill 编译提示都包含相同的通用协议，不包含演示业务值；
6. 原有完整后端测试、前端测试和构建继续通过。

## 7. 完成标准

使用任意物品、数量和原因演示创建采购申请时，模型能从 Schema 和提示中得知绑定路径
协议，不再把具体值输出为函数调用。协议同时适用于未来 MES、ERP、HR 等系统中的
其他 Tool 和多步骤 Skill。
